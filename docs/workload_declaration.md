# Workload declaration (frozen at T1)

Status: frozen (read-only) on 2026-11-15, before any S2 validation run (2.6) and before any S3 policy tuning.
Changes require a new versioned file with reason and timing. All numbers below
are copied from `results/S2/workload/workload_stats.json` (generated by `p24.workload.build`).

## 1. Data source and version

- Source: DiffusionDB 2M metadata (`poloclub/diffusiondb`, public), file
  `data/diffusiondb/metadata.parquet` (read-only, 2,000,000 rows). Only metadata
  (prompt, width, height, user_name) is used; no images are read.
- File SHA-256: see `data/diffusiondb/metadata.parquet.sha256`
  (`eecd341187bc91c07f5994ad0660d40228ea025616fd57a509bef8323677c68f`).
- Row number = 0-based position in the parquet file (`src_row` in every request).

## 2. A/B split (prior vs. evaluation)

- Hash: `h = int(sha256(("p24-s2|" + user_name).encode()).hexdigest()[:16], 16)`;
  `h` even -> half A (prior / development), `h` odd -> half B (evaluation).
  Salt string: `p24-s2|`. The split is by user, so no user appears in both halves.
  Deviation from the project plan, which proposed a prompt-hash split: splitting by user was chosen
  (decision 2026-11-15) so that the evaluation half comes from users never seen in the prior half; a
  prompt split would place the same user's prompts and shape habits on both sides.
- Missing user_name: 116 rows (0.0058%; all are null, none is an empty string) are split by
  `h = int(sha256(("p24-s2|prompt|" + prompt).encode()).hexdigest()[:16], 16)` with the same parity rule
  (56 rows fall in A, 60 in B).
- Alternative split (report-only, never used to draw traces): all rows split by the prompt hash
  `("p24-s2|prompt|" + prompt)`. Its user-level leakage is expected (same user on both sides).
- Split file: `results/S2/workload/split_A_B.parquet` (columns `row`, `half`), SHA-256 in `.sha256`.
- Result: A = 1,017,602 rows / 5,059 users; B = 982,398 rows / 5,117 users (10,176 users total).
  Top-10 users hold 7.78% of A rows (largest 2.51%) and 3.96% of B rows (largest 0.56%).
- Total variation (TV) distance of the 4-resolution distribution between A and B:
  0.01099 (user split, primary) vs 0.00155 (prompt split, alternative). The user split is the
  stricter test of generalization to unseen users; the larger TV distance is expected.
- Rule of use: development traces and all strategy tuning use A and development seeds only;
  evaluation traces use B and evaluation seeds only. No evaluation trace is generated in S2.

## 3. Resolution mapping (changes pixel counts)

Let `a = width / height` of the original image. Shape keys are `(H, W)`.

| condition | mapped shape | meaning |
|---|---|---|
| `a < 0.9` | H768 x W512 | portrait |
| `a > 1.1` | H512 x W768 | landscape |
| otherwise, `width*height <= 640^2` | H512 x W512 | small square |
| otherwise | H768 x W768 | large square |

This mapping deliberately changes the pixel count of the original request: the main model (SD1.5 +
LCM-LoRA, "M1") is native at 512, so original resolutions are folded onto four buckets that the model
supports, rather than reproducing the raw DiffusionDB sizes.

Mapped distribution over all rows: H512xW512 53.01%, H512xW768 19.43%, H768xW512 24.10%,
H768xW768 3.45%. Within A: 53.55 / 19.27 / 24.01 / 3.17 %; within B: 52.45 / 19.60 / 24.20 / 3.75 %.
Raw aspect shares: a<0.9 24.10%, 0.9<=a<=1.1 56.46%, a>1.1 19.43%.

## 4. Declared batch / CFG distribution (declared, not measured)

- Batch size B in {1, 2, 3, 4} with probabilities 0.55 / 0.20 / 0.10 / 0.15 (B=3 exists to exercise padding).
- CFG on (guidance 1.5; off = guidance 1.0, no CFG) with probability 0.3.
- B and CFG are independent of each other and of the shape.
- **These values are declared, not measured.** No public source for them was located;
  public basis: unverified. A sensitivity sweep is deferred to the S3 simulator.
- B = 8 is excluded (largest declared B is 4; memory risk).

## 5. Scenarios (closed-loop arrival order, no arrival times)

A request has fields `req_id, prompt, H, W, B, cfg (0/1), noise_seed, src_row`.
Prompts come from rows drawn uniformly with replacement from the chosen half. Generation is
deterministic: the RNG is `numpy.random.default_rng(int(sha256("p24-s2|{scenario}|{N}|{seed}|{half}")[:16], 16))`,
so the same `(scenario, N, seed, half)` yields byte-identical output (checked by SHA-256 and by
`tests/test_workload.py`).

- **W1** single shape: every request 512x512, B=1, no CFG.
- **W2** skewed: shape from the drawn row's mapped resolution; B and CFG from the declared distribution.
- **W3** uniform: resolution uniform over the 4 shapes, B uniform over {1,2,3,4}, CFG per declaration.
- **W4** mid-run drift: first N//2 requests as W2; for the remaining requests portrait and landscape
  are swapped (squares unchanged).
- **W5** cold-start burst: the first 32 requests are a random permutation of all 32 shapes
  (4 resolutions x B in {1,2,3,4} x CFG on/off), so the first `max(32, ceil(0.05*N))` requests
  (50 for N=1000) cover every shape; all remaining requests as W2.

## 6. Validation streams (from A only, development seeds)

- **V1**: W1, N=400, seed 0.
- **V2**: skewed 8 shapes, N=300, seed 1. Shapes = the 8 most probable under
  (A's mapped distribution) x (declared B, CFG); if none has B=3, the 8th is replaced by the most
  probable B=3 shape. Requests drawn i.i.d. from the renormalized probabilities.
  Selected (H,W,B,cfg): (512,512,1,0), (768,512,1,0), (512,512,1,1), (512,512,2,0), (512,768,1,0),
  (512,512,4,0), (768,512,1,1), (512,512,3,0); covered raw probability mass 0.669 (B=3 was already
  in the top 8, no replacement).
- **V3**: cold-start burst of 12 shapes, N=200, seed 2: top 12 shapes as above (B=3 guaranteed), the first 12
  requests cover each shape once (random order), the rest drawn from the renormalized probabilities.
  The 12 shapes are V2's 8 plus (768,512,2,0), (512,512,2,1), (512,768,1,1), (512,768,2,0); covered mass 0.794.
- Exact probability tables: `results/S2/workload/workload_stats.md`.

## 8. Why 640x640 is not a candidate shape

Raw 640x640 images are 0.59% of DiffusionDB rows, so it is not representative of the workload.
Raw images with area <= 640^2 are 79.83% and with area <= 768^2 are 92.80%. The mapping uses
640^2 only as the area threshold separating the two square buckets (so a raw 640x640 image maps to 512x512).

## 9. How to regenerate

```
source ops/project_env.sh && export CUDA_VISIBLE_DEVICES='' && cd code
"$PROJ_PYTHON" -B -m p24.workload.build      # ~10 s, CPU only
"$PROJ_PYTHON" -B -m pytest tests/test_workload.py -q
```

Code: `code/p24/workload/{split,generate,build}.py`. Outputs under `results/S2/workload/`
(`dev_traces/`, `validation_streams/`, `split_A_B.parquet`, `seeds.json`, `workload_stats.json|md`,
`sha256_manifest.txt` for all trace files).

## 10. Limitations to state in the paper

- B/CFG distributions are declared assumptions, not measured; DiffusionDB has no batch information.
- DiffusionDB prompts were generated with Stable Diffusion on a public Discord service in 2022 and are
  used here only as a source of prompts and shape skew, not as a model of serving arrivals.
- Closed-loop order only: no arrival times, so queueing delay is out of scope.
